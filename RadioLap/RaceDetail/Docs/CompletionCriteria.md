# 레이스 상세 완료기준

[기능 목적](../README.md), [현재 작업 범위](../AGENTS.md#현재-작업-범위와-상태), [Repository 계약](RepositoryContract.md), [UseCase 계약](UseCaseContract.md)과 [화면 상태 계약](PresentationState.md)을 바탕으로, 기능이 올바르게 동작하기 위해 지켜야 할 사항을 정의합니다.
기준 충족 여부는 실제 검증 결과로 판단하며, 구현이나 테스트 코드의 존재만으로 완료로 판단하지 않습니다.

## 검증 경계

기능의 완료기준은 아래 세 영역의 입출력에서 검증합니다.

| 대상 | 검증 책임 |
| --- | --- |
| Repository | sessionID를 사용한 요청, 참가자·결과 응답 해석·식별자 연결·RaceDetailCandidate 변환, 중복·결과 부재·미연결 결과 보존, 전체 실패·취소 전달. 반환 순서는 보장하지 않는다. |
| UseCase | 입력 Race 보존, 참가자·결과 후보 조회·정규화·중복·정합성 처리, RaceDetail 구성, 정상 빈 참가자, 실패 전달·취소 전파. 반환 순서는 보장하지 않는다. |
| Presentation | 최초 조회·재시도·취소·요청 유효성 관리, 상태 전환, 표시 그룹·정렬·안내, 드라이버 선택·복귀. |

Repository의 기대값은 정제 전 후보이며, 정제된 상세는 UseCase에서 확인합니다. Presentation은 UseCase의 값을 다시 정제하지 않고, 표시할 그룹과 순서를 구성합니다. 상태·요청·데이터 처리 검증과 화면 배치·선택·복귀·스크롤 보존의 직접 화면 검증을 구분합니다.

## 1. 상세 데이터 요청

### 조회 시작과 재시도

- ViewModel은 선택한 Race와 UseCase를 받아 idle로 시작하며 초기화 자체로 조회하지 않는다. 화면 수명 동안 같은 Race를 사용한다.
- 상세에 처음 진입하면 화면이 load()를 한 번 호출한다. load()는 모든 상태에서 즉시 loading으로 전환하고 같은 Race로 조회한다.
- 조회 실패 후 ‘다시 시도’, 취소 후 ‘다시 불러오기’를 선택하면 load()로 새 조회를 시작한다.
- UseCase는 입력 Race의 sessionID만 Repository에 전달한다. UseCase와 Repository는 식별자의 숫자 범위를 별도로 제한하지 않는다.
- 세션·대회 기본 정보와 결승·취소·시즌·종료 여부 판정은 목록에서 제공한다. 상세에서 재조회하거나 재판정하지 않는다.
- 상세는 선택한 race.sessionID에 해당하는 참가자·결과 자료만 요청한다. 드라이버별 추가 요청이나 라디오·랩·스틴트 조회는 하지 않는다.

### 실패 전달과 조회 취소

- 필요한 자료의 조회·읽기·해석 실패를 Repository가 오류로 전달하고, UseCase는 이를 숨기거나 빈 성공으로 바꾸지 않는다.
- 상세를 떠날 때 cancel()을 호출한다. 진행 중인 요청이 있으면 취소·무효화하고 즉시 cancelled로 전환하며, 없으면 현재 상태를 유지한다.
- UseCase는 호출 취소를 Repository에 전파하고 자체 검증·정규화·중복 처리도 취소에 협조한다. Repository와 UseCase는 관찰한 취소를 CancellationError로 전달한다.
- 자료 공급에서 전달된 취소도 CancellationError로 전달하며, 일반 실패와 구분한다. 오류와 취소가 겹치는 경우의 처리는 각 계약을 따른다.
- 현재 유효 요청이 CancellationError로 끝나면 cancelled로 전환하며 자동 재조회하지 않는다.

### 요청 유효성과 늦은 응답

- load()를 다시 호출하면 기존 요청을 취소·무효화하고 새 요청을 시작한다.
- 마지막 유효 요청의 결과만 반영한다. 이전 요청의 늦은 성공·실패·취소와 요청 교체로 발생한 취소는 현재 상태를 변경하지 않는다.

## 2. 받은 데이터 처리

### 응답 해석과 값의 의미 — Repository

- 드라이버 이름·약칭·팀 이름은 full_name·name_acronym·team_name을 사용한다. 필수 이름의 문제를 다른 이름 필드로 보충하지 않는다.
- 사용하는 필드의 필수성·타입·Int 표현 범위는 Repository 계약에 맞게 해석한다. 세션 식별자·드라이버 번호·순위의 정수 값을 그대로 보존하고 별도의 최솟값·최댓값을 적용하지 않는다. 타입 오류나 Int 표현 범위 초과를 기본값이나 정상적인 부재로 바꾸지 않는다.
- 필수 문자열은 공백과 빈 문자열을 포함해 보존한다. 선택 문자열의 누락·null은 nil로 표현하되 빈 문자열과 공백은 UseCase가 정규화하도록 유지한다.
- 유효한 응답의 미사용 필드와 알 수 없는 필드는 무시한다. 사용하는 필드의 오류나 응답 구조 오류는 전체 실패로 전달한다.

### 식별자 연결과 후보 보존 — Repository

- 참가자와 결과는 session_key와 driver_number로 연결한다. 이름·배열 순서·순위로 연결하지 않는다.
- 요청 sessionID와 다른 session_key가 있으면 전체 실패로 처리한다. 정상 자료와 함께 있어도 조용히 제외하지 않는다.
- meeting_key는 미사용 필드로 취급하며 대회 연결을 다시 검증하지 않는다.
- 참가자에 연결되지 않은 결과는 unmatchedResults에 보존한다. 참가자를 생성하거나 해당 결과를 버리지 않는다.
- 참가자·결과의 동일·상충 중복을 보존하고 임의로 후보를 제거하지 않는다.

### 기본 정보 보존과 결과 정합성 — UseCase

- 입력 Race를 RaceDetail.race에 그대로 보존한다. sessionID·season·name·startsAt·location을 다시 정규화하거나 조회 값으로 덮어쓰지 않는다.
- 시즌은 Race.season을 사용하며 날짜에서 계산하지 않는다.
- 참가자에 연결되지 않은 결과가 있으면 전체 실패로 처리한다.

### 문자열 정규화 — UseCase

- 조회한 드라이버 이름·약칭·팀 이름의 앞뒤 공백·탭·개행과 Unicode 공백을 제거한다.
- 내부 공백·개행, 대소문자·악센트·구두점은 보존한다. 이름에서 약칭을 만들거나 약칭의 길이·대문자 표기를 강제하지 않는다.
- 정규화 후 필수 이름이 비면 전체 실패로 처리한다. 선택 정보가 비면 nil로 반환하고 다른 정보는 유지한다.

### 중복과 충돌 — UseCase

- 정규화한 참가자 정보와 연결 결과를 기준으로 동일 중복은 하나로 합치고, 사용하는 값이 상충하면 전체 실패로 처리한다. 참가자 정보와 연결 결과를 각각 확인하여 드라이버 번호별로 하나의 참가자를 반환한다.
- 정상 레코드가 함께 있어도 잘못된 레코드나 충돌을 숨기지 않는다. 서로 다른 레코드의 필수 정보를 짜깁기하지 않는다.
- 후보와 연결 자료의 입력 순서를 바꿔도 최종 값과 성공·실패 여부는 같다. 반환 배열의 순서나 여러 오류 중 먼저 보고되는 사유까지 같도록 요구하지 않는다.

### 결과 구분과 정상 빈 참가자 — Repository·UseCase

Repository는 결과 레코드의 존재와 값을 보존하고, UseCase는 이를 참가자별 최종 결과에 유지한다.

- 결과 레코드가 없는 경우와 결과가 있으나 순위가 없는 경우를 구분한다. 전자는 result 부재, 후자는 result.position의 nil로 반환한다.
- 결과 레코드의 순위 필드가 누락되거나 null이면 position을 nil로 반환하며, 해당 결과와 경기 상태는 유지한다.
- DNF·DNS·DSQ는 각각 필수 Boolean으로 해석하고 독립적으로 보존한다. 필드 오류를 false나 결과 미제공으로 바꾸지 않는다.
- 상태 플래그 때문에 순위를 제거하거나 여러 상태 중 하나를 임의로 선택하지 않는다. 모두 false여도 완주를 추정하지 않는다.
- 제공된 순위 사이의 공백과 서로 다른 드라이버의 같은 순위를 보존한다. 임의 순위를 부여하지 않는다.
- 일부 또는 모든 결과가 없어도 참가자는 유지한다. 결과 미제공을 미발표·미출발·미완주로 단정하지 않는다.
- 참가자와 결과가 모두 비면 입력 Race와 빈 참가자 목록을 반환한다. 미연결 결과·조회 실패와 구분한다.
- 조회한 참가자의 필수 정보나 참가자·결과의 정합성에 문제가 있으면 전체 실패로 처리한다. 잘못된 참가자를 제외한 부분 성공으로 바꾸지 않는다.

## 3. 화면 표시와 선택

### 조회 상태 표시

- 레이스 기본 정보는 idle·loading·content·empty·failed·cancelled의 모든 상태에서 유지하며, 모든 상태에서 목록으로 돌아갈 수 있게 한다.
- 드라이버 영역은 loading에서 로딩 표시를 보여준다.
- 참가자가 있으면 content로 드라이버 그룹을 표시하고, 없으면 empty로 “참가 드라이버 정보가 없습니다”라고 안내한다.
- failed에서는 내부 오류 종류와 관계없이 “레이스 정보를 불러오지 못했습니다.”와 ‘다시 시도’ 버튼을 표시한다. 실패를 부분 결과나 정상 빈 참가자로 표시하지 않는다.
- cancelled에서는 오류 안내 없이 ‘다시 불러오기’ 버튼을 표시한다.

### 레이스와 드라이버 정보 표시

- 입력 Race의 시즌·대회 이름·결승 시작 날짜·장소와 결승 표시를 제공한다. 시각은 표시하지 않는다.
- 날짜는 기기 시간대를 적용한다. 시간대 변경 후 다시 표시해도 원본 절대 시각과 드라이버 순서를 유지하고, 시간대 변경만으로 재조회하지 않는다.
- 장소가 없으면 ‘장소 정보 없음’, 팀 이름이 없으면 ‘팀 정보 없음’을 표시한다. 약칭이 없으면 약칭 영역을 숨기고 이름을 유지한다.
- 드라이버 이름·약칭·팀 이름과 제공된 순위·경기 상태를 표시한다. true인 상태는 모두 ‘DNF · 미완주’, ‘DNS · 미출발’, ‘DSQ · 실격’으로 표시한다.
- 조회하지 않은 라디오 개수를 0개나 ‘공개 라디오 없음’으로 표시하지 않는다.

### 그룹과 표시 순서

Presentation이 아래 그룹과 순서를 구성하며, Repository와 UseCase의 반환 순서에 의존하지 않는다.

| 표시 순서 | 대상 | 그룹 내 순서 |
| --- | --- | --- |
| 1. 순위 있는 드라이버 | 결과와 순위가 있는 참가자 | 순위 오름차순, 동률이면 드라이버 번호 오름차순 |
| 2. 순위 없음 | 결과는 있지만 순위가 없는 참가자 | 드라이버 번호 오름차순 |
| 3. 결과 미제공 | 결과 레코드가 없는 참가자 | 드라이버 번호 오름차순 |

- 빈 그룹은 숨긴다. 결과 미제공 그룹에는 “아직 결과가 제공되지 않았습니다”라고 안내한다.
- 전체 인원수는 결과 미제공 참가자를 포함한 참가자 수이며, 그룹 인원수는 해당 그룹의 참가자 수이다.
- 상태 플래그 때문에 순위나 그룹을 바꾸지 않는다. 표시 순서로 새로운 성적을 부여하지 않는다.

### 드라이버 선택과 복귀

- 모든 그룹에서 드라이버를 선택할 수 있다. 순위 없음·DNF·DNS·DSQ·결과 미제공으로 선택을 막지 않는다.
- 선택 시 race.sessionID와 driverNumber를 다음 라디오 화면에 전달한다. 이름·순위를 식별자로 사용하지 않는다.
- 라디오 화면에서 상세로 돌아오면 재조회하지 않고 기존 결과와 보던 스크롤 위치를 유지한다.
- 상세에서 목록으로 돌아오면 재조회하지 않고 목록의 기존 목록과 보던 스크롤 위치를 유지한다.
- 목록 복귀 후 레이스를 다시 선택하면 새 상세 조회를 시작한다.

## 적용 범위

참가자·결과를 조회하는 실제 API Provider 구현은 현재 범위에 포함합니다. 라디오 조회·재생·대사 생성과 공개 라디오 개수 표시는 포함하지 않습니다. 와이어프레임의 검토용 버튼·선택 제한·예시 데이터도 제품 로직으로 고정하지 않습니다.

## 실제 API 연동 검증

- drivers·session_result 경로와 선택한 세션의 session_key 필터가 계약과 일치한다.
- 정상 JSON과 빈 배열을 기존 Domain 모델로 변환한다.
- HTTP 실패(429·5xx 포함), 통신 실패·시간 초과·잘못된 JSON을 빈 결과로 숨기지 않는다.
- 요청 취소를 전송에 전파하고 CancellationError로 전달한다.
- 실제 API에서도 기존 참가자·결과 연결, 결과 정제·정렬과 상세 화면 상태·선택·복귀 정책을 유지한다.
- 자동 테스트와 실제 API·화면 확인 결과는 별도로 보고한다.

- 데모와 API는 별도 Repository 구현체이며, 파일 공급과 네트워크 요청 책임을 분리한다. 공통 DTO와 각 Provider의 연결·변환 로직에 동일한 계약을 적용하고 두 경로의 테스트를 각각 유지한다.
